# FAIR Data Demo for the people who run it

A guide for engineers, data architects and platform staff evaluating what this
demonstration actually does, and what would change in your own estate.

The FAIR Data Demo models three federal health releases, NHANES 2017-2018,
BRFSS 2022 and the CMS DE-SynPUF Medicare sample, as seven SDC4 data models
composed from the published component libraries, and runs the seven
applications SDCStudio generated from them on your machine with `make demo`.
This document explains the parts that are easy to miss, including what the
first build of this demonstration got wrong and this one fixes in the open.

## Getting it running

Docker or Podman with the compose plugin, about 10GB of free RAM for the
containers, Python 3.12 on the host for data generation only, and the three
federal source files, which are public and need no registration.

```bash
git clone https://github.com/SemanticDataCharter/FAIR_Data_Demo.git
cd FAIR_Data_Demo
# download the files listed in source_data/README.md into source_data/
python3 -m pip install pyreadstat pandas
python3 scripts/convert_xpt_to_csv.py     # NHANES and BRFSS are SAS transport files
make demo
```

That starts the stack, generates the sampled dataset from the source rows and
loads it. Generation takes about three minutes; loading takes about 107 minutes,
almost all of it validation and the write into both stores. Then open
`http://localhost:18100/console/`.

No account is created and nothing leaves the machine. The first run needs the
network for two things only: pulling the container images and installing the
host-side generator requirements. After that the stack is self-contained:
schemas resolve through a local OASIS catalog at
`app/sdc4/mediafiles/dmlib/catalog.xml` instead of fetching `sdc4.xsd` over
HTTP, and all CSS and JS are vendored under `app/sdc4/static/vendor/`.

**A correct run is reproducible, so check the numbers before you trust
anything else here:** 84,352 records across 7 models, 84,352 named graphs in
GraphDB, 0 records stating an absence. Record count and graph count must
match. If they do not, see the orphaned-graph note in section 6.

---

## 1. The applications are generated. The model is the source of truth.

All seven applications were generated by SDCStudio from the published data
models. Nobody wrote seven Django apps. **When the model changes, the
applications are regenerated, not patched.**

The practical test of this claim is in the repository: `app/sdc4/*/` are
generated, `app/sdc4/mediafiles/dmlib/` holds the published model per app,
`sdcstudio_downloads/` holds the packages and apps exactly as downloaded, and
every generated app reads its own schema from the library.

The demonstration data is generated the same way. No generator carries an
element identifier, an element order or an XML envelope: each one names the
facts a source row has by their label path in the published model, and
`datagen/engine.py` fills the model's own instance template (`dm-<ct_id>.xml`,
shipped by SDCStudio beside the schema), drops what was not given, and refuses
a value of a shape the schema does not allow. When a model is republished the
generators do not change; the ids they never carried are read from the new
schema. `datagen/tests/` generates records into a temporary directory and
validates each against its schema, so the numbers on the console are the
numbers the schema agreed to before the loader saw them.

## 2. One record, three projections, no ETL between them

Every instance is validated once and then written to PostgreSQL and to the
triple store from the same source. Open any record in the console at
`/console/` and switch between the tabs:

| Projection | Where it comes from | What it is |
|---|---|---|
| Document | `xml_content` | the authoritative artifact that was validated |
| Table | `json_instance` | a JSON projection generated from that XML |
| Graph | the named graph in GraphDB | RDF generated from the same XML |

There is no pipeline between them and no reconciliation step. The graph is not
a copy that drifts, it is a projection.

## 3. A refused answer is left out and counted, never averaged

Survey files encode missingness as values. NHANES writes 7 for "refused" and 9
for "don't know"; BRFSS writes 7 and 9, or 77 and 99, depending on the width
of the answer; CMS leaves the cell blank. Every one of those parses downstream
as a real value unless something stops it. A 9 in a "days smoked" column is
nine days.

The generators read the agencies' missing-value codes per variable and do not
write the leaf. Every leaf in these models is optional, so the record is valid
and asserts nothing about the answer. The counts of what was left out are
printed per variable when the data is generated, so the omission is
accountable: in the sampled BRFSS run, 924 respondents did not state their
income and 402 did not name their insurance, and neither number is in the
store as a category.

Where a model *requires* a value and the row has none, SDC4 has the other
form: an ISO 21090 null flavor (`ASKU`, `ASKR`, `NI`) naming the reason, and
the record fails validation on purpose. No model in this demonstration requires
a survey answer, so no record here does that; the CordovaOS demonstration
shows that path.

**What to check in your own data:** search for your sentinels. `7`, `9`,
`77`, `99`, `9999`, `-1`, `UNKNOWN`, blank. Each one is a question your schema
cannot ask.

## 4. The join is the component, not a mapping table

Three studies compose one component library. Where two studies mean the same
thing, they compose the *same published component*, identified by its
`ct_id`, not two local conventions that a mapping table later reconciles.

The models compose four libraries by identifier slot
(`https://axius-sdc.com/library/<library>/<key>`): Default for the person,
gender, birth date and money; NIH CDE for race and ethnicity, age, education,
marital status, income, insurance and employment; FHIR for blood pressure,
vital signs, laboratory results, encounters, coverage and medication orders;
ProvGov for provenance and audit. What the studies share and no library holds
is authored once in this project: smoking status on the LOINC 72166-2 answer
list, twenty-one chronic-condition indicators each with a SNOMED CT subject
and a companion basis component ("told by a health professional" or "found in
claims"), general health, veteran status. Every study that measures one
composes the same one.

Counted from the records in GraphDB, not from the schemas or the generators:
the query groups field reifiers by the component in their IRI and counts the
distinct models and records carrying each. The page prints it. The first visit
after a load computes it (about two minutes over 33 million triples, with the
conditions question after it); the answers are cached, keyed by the record
count, until the next load.

What is deliberately *not* shared is as instructive. The CMS claims carry
ICD-9-CM diagnoses and procedures and HCPCS line codes as coded values owned by
this project, because that is what 2008-2010 claims were coded in and the FHIR
library's condition component is ICD-10-CM. A claim's diagnosis is not
silently promoted to a code system it was not coded in. Survey weights, PSU
and stratum are components with the agency's definition, because a reader who
wants a weighted estimate needs them.

## 4a. The graph is derived, not stored

Every query result in the demo has a Graph tab. There is nothing to draw in the
triple store itself: a record there is a hub of field reifiers, and no triple
links one record to another. `demo/entity_graph.py` builds the picture after
the query from the records it returned, in two ways, because this
demonstration has two kinds of join:

- **Within a study, the subject identifier.** An NHANES participant and their
  medication rows share a SEQN; a CMS beneficiary and their claims share a
  DESYNPUF_ID. A shared value is drawn as a node with an edge to every record
  carrying it, labelled by the component. A value only one record carries is
  not a join and is not drawn.
- **Across studies, the component.** The three populations are different
  people, so no value joins an NHANES record to a BRFSS record. What joins them
  is that both carry Smoking Status, the same component. The graph draws one
  node per shared component and an edge from every record of every study that
  carries it, labelled with that record's value. Two studies meet at the
  component, which is the claim of this demonstration made visible.

The layout is a seeded force layout in `static/demo/entity_graph.js`, no graph
library, so the same result draws the same picture on every machine.

## 5. Governance is read from the published schema

Select any field in the table projection and the console reports what the
model permitted it to hold: the reference model type it restricts, the facets
on its value, whether the value is required, its units, whether an absence may
be stated, the definition, and the external binding.

For Systolic Blood Pressure that is the FHIR library's component, an
`XdQuantityType` in mmHg with its range; for Smoking Status it is the FAIR
component with the LOINC 72166-2 answers enumerated and `skos:exactMatch` to
the LOINC code. None of that is a description someone maintained separately.
It is parsed from `dm-<ct_id>.xsd`, the same file a counterparty validates
against.

## 6. Operational notes, learned the hard way

- **Every instance is projected to the triple store, invalid ones included.**
  A record that failed validation is a fact someone may be looking for. Each
  named graph carries `sdc4:validationStatus`, so a consumer who wants only
  clean data writes one `FILTER`.
- **The loader takes the batch path by default.** `load_all_data --batch 200`
  builds each model's XSD 1.1 schema once, writes rows in batches, and sends a
  batch of named graphs to GraphDB in one TriG request. `--batch 0` is the
  one-record-at-a-time path the generated apps ship, which does the same work
  per record and rebuilds the schema for each; it is an order of magnitude
  slower. The records are large (a BRFSS respondent is a few hundred triples),
  so a batch commit in GraphDB is the visible cost; the load log prints per
  model, not per batch, and the row count in PostgreSQL is the live progress.
- **Clearing loaded data means clearing the triple store too.** `--clear`
  drops the named graphs by name, a thousand per update, and then drops any
  graph left by a model no longer registered. Pattern deletes over tens of
  thousands of graphs stall, and an interrupted GraphDB transaction can corrupt
  the repository; if that happens, delete the repository through GraphDB's
  REST API and restart the web container, which recreates it.
- **Keep schema resolution local.** Every generated schema includes
  `sdc4.xsd` by URL. `mediafiles/dmlib/catalog.xml` maps it to the local copy
  so validation is the same on an air-gapped host as on a connected one.
- **SirixDB authenticates against a Keycloak realm.** The realm import file is
  `mediafiles/keycloak/import/sirixdb-realm.json`, tracked in the repository.
  If SirixDB exits with "Realm does not exist", Keycloak started without it;
  check the directory's ownership (a container can create it root-owned) and
  recreate Keycloak.
- **`settings._discover_local_apps()` scans every directory with an
  `apps.py`.** A hand-registered app must also be added to that function's skip
  set, or Django refuses to start with "Application labels aren't unique".
- **The instance template writes a component composed in several clusters
  once, and cuts a label at an apostrophe.** Both are SDCStudio defects the
  engine repairs from the schema (issues #705 and #706); the generators name
  the full label and the engine completes the template.

## 7. What this demonstration does not show

- Medications do not join across studies: NHANES names the drug and carries
  its own identifier, CMS carries an NDC, and neither is RxNorm. The
  walk-through's fifth beat shows the gap.
- Education and income are not harmonized: the NIH CDE lists do not nest with
  the agencies' bands, so those leaves carry the agency's codes only.
- BRFSS 2022 did not ask about blood pressure or cholesterol.
- There is no person-level join across studies; the populations are different
  people.
- The full files are about 7 million records. Generation handles them
  (`make generate-full`); loading them at the measured rate is days, and is
  not a laptop target.

## Running it

```bash
git clone https://github.com/SemanticDataCharter/FAIR_Data_Demo.git
cd FAIR_Data_Demo
# source files into source_data/, converted once, then
make demo          # Docker, ~10GB RAM
```

Then open `http://localhost:18100/demo/` for the dashboard and walk-through and
`http://localhost:18100/console/` for the record console.
